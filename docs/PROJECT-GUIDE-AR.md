# شرح المشروع وتقسيم المسؤوليات

ده ملف شرح ليك، منفصل عن `API.md` اللي هتسلّمه لمطور الفرونت. هنحدّثه مع كل شاشة لحد النسخة النهائية. الشرح بالعربي، لكن أسماء الخدمات وكل الكلام داخل التطبيق بالإنجليزي زي ما اتفقنا.

## وصلنا لفين؟

1. قائمة الخدمات: dictionary مفاتيحها `electricity` و`water` و`gas`، وكل قيمة قائمة بالخدمات التابعة للقسم.
2. الاستعلام: المستخدم يختار خدمة ويدخل رقم المشترك ويضغط `Check my bill`.
3. تفاصيل الفاتورة: لو الاستعلام نجح، تظهر بيانات الفاتورة والمبالغ والوقت المتبقي تلقائيًا.

الدفع التجريبي وشاشة نجاح الدفع اتنفذوا. وجود فاتورة لوحده لا يعني إنها اتدفعت. حاليًا مفيش Auth ولا قاعدة بيانات ولا اتصال بشركات خدمات حقيقية.

## لما يدوس على الزرار وفيه فاتورة، هينقل إزاي؟

مثال: المستخدم اختار `Cairo Electricity` وكتب `1024750891`.

1. الفرونت يتأكد مبدئيًا إن الرقم 10 أرقام ويشيل مسافات العرض. الرقم يفضل نص، عشان أي أصفار في بدايته ما تضيعش.
2. الفرونت يوقف الضغط المتكرر ويغيّر الزرار لـ `Checking…`، ويبعت طلب `POST /api/v1/inquiries` فيه `serviceId` و`subscriberNumber`.
3. الباك إند يعيد التحقق من البيانات، ويتأكد إن الخدمة موجودة ومتاحة وإن المشترك عنده فاتورة تجريبية.
4. الباك إند يحسب الرسوم والضريبة والإجمالي، ويرجع `200 OK` ومعاه بيانات الفاتورة في JSON.
5. الفرونت يستقبل النجاح ويحفظ الرد مؤقتًا، وبعدها **هو اللي ينقل المستخدم لشاشة Bill details** ويعرض نفس البيانات.

**الباك إند مش بيفتح صفحة على جهاز المستخدم، ومش بيرجع Redirect. هو بيرجع نتيجة وبيانات؛ الفرونت مسؤول عن التنقل والعرض.**

في المعاينة اللي عملناها، السطر `showBillDetails(result)` داخل `preview.js` هو اللي بيعرض الشاشة التالية. بيخفي جزء الاستعلام ويظهر جزء التفاصيل داخل نفس الصفحة، ولذلك عنوان المتصفح بيفضل `/`. ده تنفيذ بسيط للمعاينة، مش شرط مطور الفرونت يستخدم نفس الأسلوب.

لو مطور الفرونت بيستخدم React مثلًا، ممكن يحفظ الرد في state مشتركة ثم يستخدم router للانتقال لصفحة التفاصيل. اسم المسار يحدده هو. `/bill-details` في المثال الموجود بملف API مجرد مسار مقترح للفرونت، مش endpoint موجود في الباك إند.

## لو مفيش فاتورة أو حصل خطأ؟

الفرونت يفضل على شاشة الاستعلام ويعرض رسالة الخطأ. ما ينقلش للتفاصيل لمجرد إن المستخدم ضغط الزرار، وما يعرضش فاتورة من محاولة قديمة.

| الحالة | نتيجة الباك إند | سلوك الفرونت |
| --- | --- | --- |
| رقم أقل أو أكثر من 10 أرقام | 400 | يوضح إن الرقم غير صحيح |
| خدمة غير متاحة | 409 | يوضح إن الخدمة غير متاحة |
| مشترك غير موجود | 404 مع SUBSCRIBER_NOT_FOUND | يعرض رسالة عدم وجود المشترك |
| لا توجد فاتورة مستحقة | 404 مع NO_OUTSTANDING_BILL | يعرض رسالة عدم وجود فاتورة |
| فاتورة موجودة | 200 وبيانات الفاتورة | ينتقل للتفاصيل |
| الاتصال قطع | لا يوجد رد صالح | يعرض رسالة إعادة المحاولة |

خلي بالك: حالتين ممكن يرجعوا نفس HTTP status زي `404`، لكن `code` يحدد السبب بالتفصيل و`message` هي الرسالة المقروءة للمستخدم.

## دورك كمسؤول الباك إند

- توفر endpoints واضحة وتشرح الطلب والرد وحالات الخطأ في ملف API.
- تتأكد من صحة البيانات على السيرفر حتى لو الفرونت عمل تحقق قبل الإرسال.
- ترجع معرف ثابت لكل خدمة، وتتحقق من حالة توفرها وقت الاستعلام.
- تحسب مبلغ الفاتورة والرسوم والضريبة والإجمالي على السيرفر بالقروش، وتحدد وقت انتهاء عرض السعر.
- توفر أرقام تجريبية وأمثلة جاهزة، وتختبرها على Postman مع مطور الفرونت.
- عند مرحلة الدفع، السيرفر لازم يحفظ عروض الأسعار والمدفوعات ويتحقق من صلاحية العرض ويمنع تكرار الدفع. ده اتنفذ حاليًا في ذاكرة السيرفر للديمو، وبيتمسح عند إعادة التشغيل.

## دور مطور الفرونت

- يبني الشاشات ويتعامل مع الضغط على الأزرار والتنقل والرجوع.
- يرسل معرف الخدمة ورقم المشترك بالشكل المتفق عليه.
- يعرض تحميل أثناء الطلب، ورسالة مناسبة عند الخطأ، وينتقل عند النجاح فقط.
- يعرض الأرقام اللي رجعت من السيرفر؛ ما يحسبش ضريبة أو رسوم أو إجمالي من نفسه.
- يعرض عداد انتهاء الصلاحية، ويتعامل مع انتهاء الوقت وفقدان بيانات الصفحة عند refresh.

## المبالغ بتتفسّر إزاي؟

القروش أعداد صحيحة: `24750` معناها `247.50 EGP`، و`500` معناها `5.00 EGP`، و`70` معناها `0.70 EGP`.

فاتورة كهرباء القاهرة التجريبية: 247.50 أصل الفاتورة + 5.00 رسوم + 0.70 ضريبة على الرسوم = 253.20 إجمالي. السيرفر بيرجع القيم الأربع بالفعل. الفرونت يحول تنسيقها للجنيه فقط، ويستخدم `totalPiastres` كما هو بدل ما يجمعها تاني.

## عداد الخمس دقائق

السيرفر بيرجع `createdAt` و`expiresAt`، بينهم 300 ثانية. الفرونت يحسب الوقت المتبقي للعرض من `expiresAt`، مش يبدأ خمس دقائق جديدة كل ما يفتح الشاشة.

عند انتهاء الوقت، المعاينة تعرض `Quote expired` وزرار `Check bill again`. الضغط عليه يرجّع للاستعلام والرقم لسه مكتوب؛ المستخدم يضغط `Check my bill` عشان ياخد عرض جديد. زرار الرجوع العادي كمان بيحافظ على الرقم.

العداد الحالي للعرض، وبيعتمد على ساعة الجهاز. الباك إند في طلب الدفع بيعيد التحقق من الصلاحية بساعة السيرفر؛ ما يعتمدش على العداد أو على إن الفرونت عطّل زرار.

حاليًا بيانات العرض موجودة في ذاكرة الفرونت والسيرفر. لو المستخدم عمل refresh بيرجع لقائمة الخدمات ويستعلم من جديد. مفيش endpoint لجلب quote قديم أو حفظ دائم للعروض؛ سجل المدفوعات متاح من GET /api/v1/payments طول ما السيرفر شغال.

## تقول إيه لمطور الفرونت؟

«لما المستخدم يدوس Check my bill، ابعت serviceId وsubscriberNumber للـ inquiry API. لو الرد 200، خزّن الرد مؤقتًا وانتقل لشاشة Bill details، واعرض الحقول الموجودة فيه. لو الرد خطأ، خليك على شاشة الاستعلام واعرض message. كل المبالغ بالقروش والباك إند حاسبها؛ دورك تنسيق العرض بس. العداد من expiresAt، ولو انتهى اعرض إعادة الاستعلام. تفاصيل الطلبات والأخطاء وربط الحقول موجودة في API.md.»

## إيه اللي هتسلّمه له؟

- `docs/API.md`: دليل التكامل والحقول والانتقال المطلوب عند النجاح والخطأ.
- `docs/openapi.yaml`: توصيف قابل للقراءة بأدوات API.
- `docs/MMKN.postman_collection.json`: طلبات وأمثلة واختبارات جاهزة للاستيراد في Postman.
- عنوان الباك إند اللي الفرونت يقدر يوصله. `localhost:8080` بيشير لنفس جهاز اللي بيشغّل الفرونت؛ على جهاز مطور تاني لازم عنوان متاح له أو يشغّل الباك إند محليًا.

الملف ده للشرح ليك، ومش محتاج تسلّمه للفرونت بدل عقد الـ API.

## تجربة سريعة قبل اختبار Postman النهائي

شغّل المشروع وافتح `http://localhost:8080/`. اختار Cairo Electricity وجرّب `1024750891`: هينقلك تلقائيًا للتفاصيل وتلاقي الإجمالي 253.20 EGP. قبل الدفع تقدر ترجع وتجرب `1024750892`: هيفضل على الاستعلام ويعرض إن مفيش فاتورة مستحقة. للدفع جرّب الرقم الأول واضغط Pay now · Demo؛ الرد الناجح هيفتح الإيصال. نتيجة الاختبارات وطريقة تشغيل Postman موجودة في `TEST-RESULTS.md`.

## تحديث: المعرفات والدفع والـ VAT

معرف الخدمة id وserviceId بقوا int: القاهرة 1، الإسكندرية كهرباء 2، شمال الدلتا 3، مياه القاهرة 4، مياه الإسكندرية 5، Town Gas رقم 6 وNatgas رقم 7. ابعت serviceId: 1 كرقم، مش "1" كنص. مفاتيح الـ dictionary لسه electricity وwater وgas. رقم المشترك نص، ومعرفات العرض والدفع UUID نصية عشان تفضل متميزة عن معرف الخدمة.

حساب الـ VAT مش مسؤولية العرض في الفرونت. ممكن الفرونت يحسب تقدير للعرض، لكن الرقم المعتمد للدفع لازم يحدده الباك إند. في InquiryService.java فيه تعليق VAT POLICY عند سطر الضريبة: لو قررت تلغيها، غيّرها لصفر وحدّث العنوان والأمثلة والاختبارات؛ ما تستقبلش ضريبة أو إجمالي من العميل وتثق فيهم. نسبة 14% هنا بيانات السيناريو التجريبي وليست معالجة ضريبية عامة.

لما المستخدم يضغط Pay now · Demo، الفرونت يبعت quoteId فقط ومعاه هيدر Idempotency-Key. الباك إند يقرأ المبلغ من العرض المحفوظ، ويتأكد إن الوقت ما انتهيش والخدمة متاحة والفاتورة ما اتدفعتش. عند النجاح يرجع إيصال، والفرونت يعرض Payment successful وينسخ المرجع عند الضغط على Copy.

لو الاتصال قطع بعد الدفع، المستخدم ما يعرفش هل الطلب نجح. عشان كده الفرونت يحتفظ بنفس المفتاح ويعيد نفس الطلب؛ السيرفر يرجّع نفس الإيصال بدون تسجيل دفعة جديدة. حتى لو مفتاح مختلف اتبعت لنفس الفاتورة، حماية الفاتورة تمنع تكرار الدفع. استخدام مفتاح عملية ناجحة لعرض مختلف يرجع خطأ تعارض.

الحفظ الحالي في ذاكرة السيرفر، بدون قاعدة بيانات: سجل الديمو موجود طول التشغيل وبيروح مع restart. الحماية دي داخل عملية سيرفر واحدة فقط. ده مناسب للتجربة المطلوبة، لكن الدفع الحقيقي يحتاج قاعدة بيانات ومعاملات وحماية تكرار دائمة. مفيش فلوس حقيقية بتتحرك.

للشرح للفرونت: «الـ serviceId رقم. عند نجاح inquiry افتح تفاصيل الفاتورة، وعند الضغط على الدفع ابعت quoteId ومفتاح ثابت لنفس المحاولة، وبعد نجاح payment افتح الإيصال من الرد. ما تبعتش VAT أو total، وما تغيّرش المفتاح عند إعادة المحاولة بعد انقطاع الاتصال.»

## الأيقونة هتبقى Image URL ولا Image Data؟

**هتبقى Image URL في حقل اسمه `iconUrl`، ونوع الحقل `string`.** مش Base64، ومش محتوى الصورة جوه JSON. نفس رسومات الكهرباء والمياه والغاز اللي في المعاينة بقت ملفات SVG منفصلة، والـ API بيرجع عنوانها.

```json
{
  "id": 1,
  "name": "Cairo Electricity",
  "available": true,
  "iconUrl": "/icons/electricity.svg"
}
```

الرابط نسبي لعنوان الباك إند. لو الباك إند شغال على `http://localhost:8080`، يبقى الرابط الكامل `http://localhost:8080/icons/electricity.svg`. لو الفرونت شغال على بورت مختلف زي 3000، لازم يضيف عنوان **الباك إند**؛ استخدام الرابط النسبي لوحده هيطلب الصورة من بورت الفرونت بالغلط.

| نوع الخدمة | الرابط في الرد | نوع ملف الصورة |
| --- | --- | --- |
| electricity | /icons/electricity.svg | SVG؛ Content-Type: image/svg+xml |
| water | /icons/water.svg | SVG؛ Content-Type: image/svg+xml |
| gas | /icons/gas.svg | SVG؛ Content-Type: image/svg+xml |

الفرونت على الويب يعرضه بـ `<img>`، وعلى تطبيق الموبايل يستخدم مكوّن بيدعم SVG. كل خدمات نفس القسم حاليًا ليها نفس الأيقونة، لكن الحقل موجود في كل خدمة عشان نقدر نغيرها لخدمة واحدة بعدين. لون الرسمة داخل ملف SVG؛ خلفية المربع وإظهار الخدمة غير المتاحة بالرمادي مسؤولية تصميم الفرونت.

في شاشة الفاتورة يجيب الخدمة من الـ dictionary باستخدام `serviceId`، وبعدها يعرض `iconUrl` بتاعها. مش محتاجين نكرر رابط الصورة داخل الفاتورة أو الإيصال. لو تحميل الصورة فشل، اسم الخدمة يفضل ظاهر. حفظ قائمة الخدمات أوفلاين مش معناه إن ملفات الصور محفوظة؛ لو لازم الصور تظهر أوفلاين، الفرونت يحفظها كمان.

## كل object ونوع كل حقل

الجداول دي بتوصف **بيانات الـ API العامة**؛ مش محتاج الفرونت يعرف المتغيرات الداخلية في السيرفر. الحقول المذكورة في الردود كلها موجودة ومش `null`، وحقول الطلبات المذكورة كلها مطلوبة.

### فهم الأنواع بسرعة

- `object`: مجموعة مفاتيح وقيم بين `{ }`.
- `array`: قائمة بين `[ ]`.
- `string`: نص بين علامتي تنصيص، حتى لو النص مكوّن من أرقام، زي رقم المشترك.
- `integer / int`: عدد صحيح زي `1` بدون تنصيص. JSON بيسميه `number`؛ Java بيستخدم `int` لمعرف الخدمة.
- `integer / long`: عدد صحيح أكبر، بنستخدمه للمبالغ بالقروش. الـ API بيوصفه `int64`.
- `boolean`: إما `true` أو `false` بدون تنصيص؛ مش `"true"` كنص.
- `UUID`: شكل خاص من النص لتعريف عرض أو عملية، مش رقم خدمة.
- `date-time`: نص ISO-8601 زي `2026-09-30T10:15:00Z`. حرف `Z` معناه UTC؛ ممكن يكون فيه أجزاء من الثانية. الفرونت يحوله للتوقيت المطلوب عند العرض.

### 1. ServiceDictionary — قائمة الخدمات

ده رد `GET /api/v1/services`. نوعه `object`، وفي Java هو `Map<String, List<ServiceItem>>`.

| المفتاح | نوع القيمة | معناها |
| --- | --- | --- |
| electricity | array من ServiceItem | خدمات الكهرباء |
| water | array من ServiceItem | خدمات المياه |
| gas | array من ServiceItem | خدمات الغاز |

الرد نفسه هو الـ dictionary مباشرة؛ مفيش طبقة اسمها `data` حواليه. أسماء الأقسام strings، لكن `id` داخل الخدمة int.

### 2. ServiceItem — الخدمة الواحدة

| الحقل | نوعه في JSON / Java | مثال | استخدامه |
| --- | --- | --- | --- |
| id | integer int32 / int | 1 | المعرف اللي يتبعت في الاستعلام |
| name | string / String | Cairo Electricity | الاسم الظاهر |
| available | boolean / boolean | true | هل يقدر يختار الخدمة؟ |
| iconUrl | string / String | /icons/electricity.svg | رابط صورة الخدمة |

### 3. InquiryRequest — طلب الاستعلام

ده اسم وصفي لجسم `POST /api/v1/inquiries`، مش لازم يبقى اسم class عند الفرونت.

| الحقل | نوعه | مثال | القاعدة |
| --- | --- | --- | --- |
| serviceId | integer int32 | 1 | رقم موجب؛ `"1"` كنص مرفوض |
| subscriberNumber | string | "1024750891" | عشر أرقام إنجليزية بدون مسافات |

أي مبالغ إضافية في طلب الاستعلام بتتجاهل؛ مش بتغير الحساب. طلب الدفع، على العكس، بيرفض أي حقول زيادة عن quoteId.

### 4. BillQuote — رد الاستعلام / بيانات تفاصيل الفاتورة

| الحقل | نوعه في JSON / Java | المثال أو المعنى |
| --- | --- | --- |
| quoteId | string UUID / String | معرف عرض السعر، يحتفظ به الفرونت للدفع |
| serviceId | integer int32 / int | 1 |
| serviceName | string / String | Cairo Electricity |
| subscriberNumber | string / String | "1024750891" |
| customerName | string / String | Mina A. |
| billMonth | string / String، بالشكل YYYY-MM | "2026-08" |
| currency | string / String | "EGP" |
| amountDuePiastres | integer int64 / long | 24750 = 247.50 جنيه |
| serviceFeePiastres | integer int64 / long | 500 = 5.00 جنيه |
| vatPiastres | integer int64 / long | 70 = 0.70 جنيه |
| totalPiastres | integer int64 / long | 25320 = 253.20 جنيه |
| createdAt | string date-time / Instant | وقت إنشاء العرض من السيرفر |
| expiresAt | string date-time / Instant | وقت انتهاء العرض، بعد 300 ثانية |

الشهر نص مش تاريخ كامل، والمبالغ أرقام صحيحة مش strings ولا كسور. مفيش iconUrl هنا؛ الخدمة تتجاب بمعرفها من القائمة.

### 5. PaymentRequest — طلب الدفع

جسم `POST /api/v1/payments` فيه حقل واحد:

| الحقل | نوعه | استخدامه |
| --- | --- | --- |
| quoteId | string UUID | نفس معرف عرض السعر الراجع من الاستعلام |

الهيدرز منفصلة عن الجسم:

| الهيدر | نوع القيمة | مثال أو شرط |
| --- | --- | --- |
| Content-Type | string | application/json |
| Idempotency-Key | string | من 8 إلى 128 حرف؛ حروف وأرقام وشرطة أو underscore؛ UUID مناسب |

نفس مفتاح المحاولة لازم يفضل ثابت لو الرد ضاع وهنعيد الطلب. ممنوع نبعت total أو VAT؛ السيرفر يجيبهم من العرض المحفوظ.

### 6. PaymentReceipt — إيصال نجاح الدفع

| الحقل | نوعه في JSON / Java | استخدامه |
| --- | --- | --- |
| paymentId | string UUID / String | معرف العملية الناجحة |
| quoteId | string UUID / String | معرف العرض اللي اتدفع أصلًا |
| reference | string / String | مرجع بالشكل MP-YYYYMMDD-UUID، يتنسخ بالكامل |
| status | string / String | "SUCCESS" |
| serviceId | integer int32 / int | معرف الخدمة |
| serviceName | string / String | اسم الخدمة في الإيصال |
| subscriberNumber | string / String | رقم المشترك |
| totalPiastres | integer int64 / long | الإجمالي المدفوع بالقروش |
| currency | string / String | "EGP" |
| paidAt | string date-time / Instant | وقت الدفع الفعلي من السيرفر، UTC |

المعاينة بتحوّل paidAt لتوقيت القاهرة عند العرض. `reference` نص حتى لو فيه تاريخ وأرقام. تكرار الدفع لنفس الفاتورة بيرجع نفس الإيصال؛ لو الطلب استخدم عرضًا آخر لنفس الفاتورة، الإيصال يفضل يشير للعرض الأصلي المدفوع.

### 7. PaymentHistory — سجل الديمو

رد `GET /api/v1/payments` عبارة عن `array<PaymentReceipt>`؛ في Java هو `List<PaymentReceipt>`. أحدث عملية الأول. السجل الفاضي يرجع `[]`، مش `null` ولا object. السجل مش شخصي لكل مستخدم لأن مفيش Auth، وبيتمسح عند restart.

### 8. ApiError — الأخطاء الموثقة

| الحقل | نوعه في JSON / Java | مثال |
| --- | --- | --- |
| code | string / String | QUOTE_EXPIRED |
| message | string / String | This quote has expired. Check your bill again. |

رقم HTTP status زي 400 أو 404 أو 409 موجود في استجابة HTTP نفسها، مش حقل داخل الـ object. المسارات الغلط أو طرق HTTP غير المدعومة ممكن ترجع شكل خطأ Spring الافتراضي؛ الفرونت ما يفترضش إن كل رد خطأ من أي مسار لازم فيه code.

### 9. ملف الصورة نفسه

طلب `GET /icons/electricity.svg` بيرجع **ملف صورة SVG** بـ Content-Type `image/svg+xml`، مش JSON object. جوه رد قائمة الخدمات فيه الرابط فقط؛ المتصفح بيعمل طلب منفصل للصورة. ده الفرق بين Image URL اللي اختارناه وImage Data اللي كانت هتتحط جوه الرد نفسه.

### بيانات تخص الفرونت فقط

`savedAt` بتاع نسخة الخدمات المحفوظة هو string وقت بيعمله الفرونت؛ مش حقل راجع من الـ API. البحث والعداد وحالة loading والشاشة الحالية متغيرات في الواجهة، مش objects لازم السيرفر يرجعها. المفاتيح النصية في JSON ثابتة بالإنجليزي؛ لغة الشرح هنا بس هي العربي.
